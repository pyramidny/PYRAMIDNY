# Pyramid Restoration Staff Portal — Database Schema Reference
> Last updated: May 2026 | Supabase project: `izjaxmcdlsdkdliqjlei`

## Tables

### `projects`
Core project record. One row per bid or job.
- `id` uuid PK
- `project_number` text UNIQUE — auto-generated by `auto_project_number` trigger
- `division` division_type enum — `regular` | `ira`
- `status` project_status enum — `New Bid` | `Active Bid` | `No Bid` | `Bid Not Awarded` | `Job Awarded` | `Active Job` | `Job Closed`
- `current_stage` smallint (1–6) — synced from status via `sync_stage_on_status` trigger
- `pm_id`, `assistant_pm_id`, `estimator_id` → FK `profiles`
- `sharepoint_folder_id`, `sharepoint_folder_url` — set by project-proxy on insert

### `profiles`
One row per staff member. Auto-provisioned on first Azure AD login via `handle_new_user_from_whitelist` trigger.
- `role` user_role enum — see Roles section below
- `division` division_type — `regular` | `ira` | null (null = access to both)
- `azure_oid` — backfilled on first login, used for JWT identity lookup

### `staff_whitelist`
Allowlist that gates Azure AD login. Staff must exist here before they can access the app.
- Seeding here does NOT create a profile — profile is created on first login.

### `project_tasks`
Workflow tasks, seeded from `workflow_task_templates` on project insert.
- `assigned_role` — the template role (e.g. `project_manager`)
- `assigned_to_id` → FK `profiles` — the specific person assigned
- `status` task_status enum — `pending` | `completed`
- `stage_number` — which workflow stage this task belongs to

### `workflow_task_templates`
Master list of tasks per stage per division. Edit here to change what tasks get auto-created on new projects.

### `project_milestones`
One row per milestone per project. Seeded by `trg_seed_milestones` trigger on project insert.
- `value` milestone_value enum — `Yes` | `No` | `Missing` | `N/A`

### `milestone_definitions`
Master list of milestones. `active_from_stage` controls when they appear in the UI.

### `notifications`
In-app notification inbox. Realtime subscription in Layout.jsx polls for unread count.
- `type` — `info` | `task` | `milestone` | `assignment` | `document`
- `is_read` — toggled by Notifications page

### `notification_settings`
Per-user preferences. Defaults to all-on. Checked by `assign_task` proxy action before writing notifications.
- `in_app`, `email`, `sms`
- `notify_new_assignment`, `notify_task_complete`, `notify_milestone_reached`, etc.

### `alert_log`
Email delivery queue for Microsoft Graph mailer (not yet built).
- `delivery_status` — `queued` | `sent` | `failed`
- `dedup_key` UNIQUE — prevents duplicate sends
- `alert_type` — `task_assigned` | others TBD

### `graph_token_cache`
Single-row cache for app-only Microsoft Graph access token. Used for SharePoint folder creation (PATH B — not yet implemented).

### `project_documents`
Metadata for files uploaded to SharePoint. SharePoint is the source of truth; this table is the index.

### `project_production`
One row per project. Tracks the production checklist (COI, submittals, permits, etc.).

### `project_activity`
Audit/activity feed. Written by triggers and proxy actions.

### `staff_audit_log`
Append-only log of all staff management actions (invite, role change, deactivate, hard delete).

## Key Triggers

| Trigger | Table | Event | Function | What it does |
|---------|-------|-------|----------|--------------|
| `set_project_number` | projects | BEFORE INSERT | `auto_project_number` | Assigns P-XXXX number |
| `auto_provision_milestones` | projects | AFTER INSERT | `provision_project_milestones` | Seeds milestone rows |
| `trg_seed_milestones` | projects | AFTER INSERT | `seed_project_milestones` | Seeds milestone definitions |
| `on_stage_advance` | projects | AFTER UPDATE | `handle_stage_advance` | Fires when stage changes |
| `sync_stage_on_status` | projects | BEFORE UPDATE | `sync_stage_from_status` | Keeps stage in sync with status |
| `log_project_changes` | projects | AFTER UPDATE | `log_project_changes` | Writes to project_activity |
| `log_task_completion` | project_tasks | AFTER UPDATE | `log_task_completion` | Writes to project_activity |
| `set_lead_time_alert` | project_tasks | BEFORE INSERT/UPDATE | `compute_lead_time_alert` | Sets lead_time_alert_at |
| `handle_new_user_from_whitelist` | auth.users | AFTER INSERT | - | Auto-provisions profile from whitelist |

## Edge Functions

| Function | JWT Verify | Purpose |
|----------|-----------|---------|
| `project-proxy` | OFF | All write operations — insert, update, assign, staff management, SharePoint, notifications |
| `create-project` | OFF | Legacy — superseded by project-proxy `insert` action |
| `update-project` | OFF | Legacy — superseded by project-proxy `update` action |
| `upsert-production` | OFF | Legacy — superseded by project-proxy |

> **Critical:** All Edge Functions must have JWT verification OFF in the Supabase dashboard. Azure AD tokens are Microsoft-signed and will be rejected at the gateway if verification is on.

## Auth Architecture

- Azure AD PKCE flow → token stored in localStorage key `sb-izjaxmcdlsdkdliqjlei-auth-token`
- `supabase.auth.getSession()` returns null for Azure AD users — always read token directly from localStorage
- All writes route through `project-proxy` Edge Function using `service_role` key
- JWT identity parsed from `oid` claim (azure_oid) with email fallback
